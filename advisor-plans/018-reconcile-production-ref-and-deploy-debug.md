## Finding

The audited checkout and the production release ref are not aligned:

- current checkout: c49e6815980561b5a7b5a42629e9211ecd42da5d
- origin/migration/vozen-rust: d0ad45df15cdbbe4dcf9117218efc5178c016b70d
- current branch is one commit ahead and one commit behind the migration branch
- the branch-only change on the migration ref is fix(voice): align streak card template
- the current branch-only change is ci: retire competing Pages publisher

The deploy workflow correctly targets migration/vozen-rust, but .github/workflows/deploy-bot.yml also has debug: true in the credential-bearing SSH action. This creates unnecessary verbose behavior around production SSH secrets. It is not evidence that a secret was printed, but it should be removed.

The release documentation is contradictory: SECURITY.md and DEPLOY.md describe main as the supported/production source, while .github/workflows/deploy-bot.yml intentionally releases from migration/vozen-rust.

## Implementation steps

1. Reconfirm the authoritative production ref with the release owner. Until confirmed, treat migration/vozen-rust as the workflow’s source of truth and do not deploy the divergent local branch.
2. Reconcile the two branch-only commits through the normal reviewed path. Preserve both intended changes, resolve conflicts explicitly, and verify that the final SHA is an ancestor of origin/migration/vozen-rust.
3. Remove debug: true from the SSH deploy action. Keep the action pinned to its reviewed commit SHA and ensure no command echoes secrets or prints the environment.
4. Update SECURITY.md and DEPLOY.md so production releases, self-hosting instructions, and support expectations consistently name the authoritative ref. Mark main as development/integration only if that is the confirmed policy.
5. Keep the existing manual production_sha input and preflight checks. Reject a release unless the SHA was produced by the successful CI run for the authoritative ref.
6. Run all Rust, voice-driver, contract, and site checks before any staging deploy. Do not bypass plan 017’s advisory remediation or use a blind lockfile update.
